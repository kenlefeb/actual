# Design

## Context

See proposal.md (Why) and `threat-model.md`. The findings and the options weighed are on sc-1950 (Security Analyst comment 1955, Architect comment 1956, PO decision 1957). This change is slice 1: the spec and the threat model, with no code. The later slices (the hosted entry, the OAuth provider, the deployment, the connection checklist) are filed when this merges.

Facts the design rests on:
- `createServer()` in `packages/mcp` is transport-agnostic; the stdio entry only connects a `StdioServerTransport`. A hosted entry calls the same function and never registers the write tools.
- The pinned `@modelcontextprotocol/sdk` (exact 1.32.1) ships `StreamableHTTPServerTransport` (with a stateless option), `createMcpExpressApp` with host-header DNS-rebinding protection, `mcpAuthRouter` with an `OAuthServerProvider` interface, `mcpAuthMetadataRouter`, `requireBearerAuth` (verifier, required scopes, expected resource) and `ProxyOAuthServerProvider`. No new dependency should be needed.
- `@actual-app/api` is a process-wide singleton: one `init` and one loaded budget per process.
- Anthropic's connectors call the server from Anthropic's infrastructure, so a tailnet-only address cannot serve them.

## Decisions

### 1. A separate entry, not a mode of the stdio entry
The hosted server is its own entry (for example `actual-mcp-http`). That keeps the stdio entry's "no listener" statement literally true, keeps the hosted entry's read-only guarantee in its own code path (it cannot be switched off by a flag it does not have), and lets the two evolve separately. Both call `createServer`, so tools, sanitizing, paging and the response cap are identical.

### 2. Stateless streamable HTTP
A fresh transport per request, no session state on the server. Read-only tools need none, and there is nothing to leak or lose. SSE is not offered (Claude documents it as deprecating).

### 3. One budget per instance, with a freshness schedule
The singleton engine means one instance serves one budget of one environment; a second budget is a second instance with its own hostname or path, credentials and data directory (`<env>-remote`). Because the process lives for days, it syncs at start and on an interval, serialized with `sync_budget` by a lock, and keeps serving the last copy when a sync fails; `get_sync_status` makes staleness visible instead of silent.

### 4. Read-only in code
`init({ readOnly: true })` is passed unconditionally (see `api-read-only-mode`), the write tools are never imported by this entry, and `--writes` is a usage error. The effect: even a compromised authorization layer cannot make the engine push or upload anything. The one remaining write path from that host is the stored sync-server password, which is why production waits for a per-budget identity (sc-1555).

### 5. Authentication: our own authorization server, one upstream identity
The server runs the SDK's authorization router with its own `OAuthServerProvider`. Its `authorize` step hands the user to a configured upstream identity provider and accepts exactly one configured account identifier; it never accepts an emailed link or code, because agents can read Ken's mail. Access tokens are opaque, short-lived and bound to the server's resource URL; refresh tokens expire after at most 30 days, are stored hashed in a 0600 state file on the instance's volume and can be revoked; rotating the signing key invalidates everything. As built (sc-1972): access tokens are HMAC-signed, last 15 minutes and carry their refresh family, so revoking the family stops them at once; refresh tokens rotate on every use, a replayed old token ends its family, and a family ends 30 days after the sign-in whatever its use; the refresh hashes are keyed with the signing key, so rotating it also strands the state file; the upstream ID token is taken straight from the provider's token endpoint over TLS, so its signature is not re-verified. The provider is configuration (issuer, client id and secret file, the account identifier), so the choice of GitHub, Google or another provider is not baked in. Rejected: an external authorization server (more internet-facing code to patch for one user), a static bearer token or secret URL (a connector cannot set one, it leaks into logs and cannot be revoked per client), and an access proxy such as Cloudflare Access (connectors cannot present its service-token headers).

### 6. Registered clients, not open registration
One pre-registered confidential client, using the custom client id and secret that Anthropic documents for servers without dynamic client registration, so no open registration endpoint faces the internet. Redirect URIs are matched exactly against a configured allowlist whose default is the documented Claude callback (`https://claude.ai/api/mcp/auth_callback`, which Anthropic says may move to a `claude.com` URL). Dynamic registration exists only behind a configuration switch, off by default, and then only for the allowlist. Always PKCE; scope `budget:read`, with the scope plumbing in place for a later `budget:write` that this change does not register.

### 7. Host, origin and rate checks
The listener binds to the configured address (loopback by default). A `Host` allowlist (the SDK's host-header validation, with the public hostname as configuration) blocks DNS rebinding. Connector traffic is server to server, so a request carrying a browser `Origin` that is not on an allowlist is refused (the SDK's check does not cover `Origin`). Every endpoint (authorization, token, revocation, MCP and the rest) is rate-limited per endpoint and per source address, with no shared counter for an endpoint, so a flood from another source cannot lock the one identity out. The engine is protected by the per-client-id limit, which runs after authentication; there is no aggregate cap across sources. The source is the last non-empty `X-Forwarded-For` entry, which the local Funnel proxy sets to the one real client address (Tailscale `serve.go` `addProxyForwardedHeaders`), and is read only when the socket peer is loopback (an IPv6 source is keyed by its /64, and an `ip:port` form is accepted). If a loopback peer gives no usable address, every such caller shares one `loopback` key, which brings back the shared limit; the entry records this once per process (`source-unresolved`, no header value). The protection is not claimed until staging confirms real client addresses in the access log. The table of sources is capped; when full the oldest-inserted is dropped, which only restarts its count.

### 8. Secrets in read-only files
Three secrets: the Actual credential, the optional encryption key and the signing key. Each is read from a file whose path is configuration, and the server refuses to start when a file is missing or readable by anyone but its owner. They never appear on a command line, in an environment value, a URL, a log, an error or a tool result. The state file holds nothing that outlives rotating the signing key.

### 9. Recording access without data
Authentication events and the name and status of each tool call are logged with the client id and time, scrubbed with the secrets list, to the container's log stream. Tool arguments and results are not logged, because they can contain budget data; this is the hosted counterpart of the write audit log, which does not apply to a read-only entry.

### 10. Exposure and deployment are configuration, decided later
Only the MCP service is public; the Actual servers stay private. **Network isolation:** the container runs on its own Docker network that reaches only the staging sync server, never with `network_mode: host` and never on a network or loopback address that production's containers use (production's Actual listens on `127.0.0.1` on the same host), and its outbound traffic is limited to that sync server and the identity provider. The deployment review checks this with `docker inspect` (network mode, networks, published ports and mounts). The exposure mechanism (a Tailscale Funnel on its own node, or a tunnel with its own edge), the hostname, the identity provider and the plaintext staging copy are Ken's decisions, needed before the OAuth slice and the deployment slice. The deployment (a compose file in actual-hosting, a container built from this repository, a separate sidecar, the secrets, the LOCKDOWN rows) is a later slice and a production-host change under Ken's gate, because staging and production share one VPS and Docker daemon.

### 11. Production: the guard (sc-2215, code in sc-2277)
The entry also validates the token against the sync server at start and exits if its user is ADMIN (the guard's conditions alone do not prove the token's privilege), and refuses a `local`-labelled server together with a non-loopback listener. The `production-remote` name is paired with a `docker inspect` mount check. Production is allowed by a deliberate, separate act, not by the stdio entry's override. The hosted entry serves a `production` host only when `ACTUAL_MCP_REMOTE_PRODUCTION=1` is set and the credential is a session token file (the assistant's token, minted by the production switch, sc-2060); a password file is refused, because the shared password opens every budget and can change itself. The allowed account must be a provider subject identifier (it must not contain `@`), so an email address, which an agent could read in a mailbox, cannot be the identity. The data directory is the instance's own `production-remote` directory. Read-only is unchanged: `readOnly: true` fixed in code, no write tool, `--writes` a usage error, so the guard widens only which budget is served, never what may be done to it. Alternatives rejected: reusing `ACTUAL_MCP_ALLOW_PRODUCTION` (an operator who set it for the stdio entry would silently open a public endpoint), and a build-time constant (it would need a second image).

### 12. Production identity (see `production-identities` and sc-2216)
Production has its own identity-provider tenant (Auth0), separate from staging's and from Ken's other app: sign-ups and social logins off, a passkey or authenticator app required, and no agent admin. It holds two users: Ken, who is ADMIN of the budget and is not the allowed connector account, and the assistant, who holds the BASIC role and is the one allowed account, named by its `auth0|...` `sub`. The sync server signs both in through the same tenant (sc-2216, fork PR #202; this change does not depend on its merge to be written, but the deployment does). The assistant's credentials are never stored in the agents' vault (Ken's decision on sc-1950). The hosted entry itself is unchanged: issuer, client, account and secrets are configuration, and the deployment review fails if any of them equals the staging instance's.

### 13. Production network and exposure
The container joins a dedicated Docker network of its own and reaches only the production sync server and the production tenant; never `network_mode: host`, never `docker.sock`, never a shared network with staging's MCP. It reaches the production sync server over that network or the tailnet and never through production's loopback address (the sync server's published `127.0.0.1` listener is not rebound or published to make this work; the deployment story chooses the route and the Architect reviews it). Exposure is its own Funnel node and hostname, running only this container's front end, with Funnel turned on for that node only (a tailnet policy step for Ken, as for staging). **Tailnet policy:** the node has its own tag (for example `tag:actual-mcp-production`) that may reach only the production sync server and has no inbound from the tailnet except Funnel; the MCP process shares the sidecar's namespace, so this policy, not the Docker rule, limits which tailnet hosts it reaches. Hardening copies staging's: non-root uid, `cap_drop: ALL`, `no-new-privileges`, read-only root, pids and memory limits.

### 14. What production requires before go-live
Staging accepted gaps that production does not. Required for production, each recorded as done before the deployment is approved:
- **Egress (sc-2203, scope widened for production): required.** Staging accepted that compose cannot limit outbound traffic. For production, a compromised container could send the plaintext production budget and the session token anywhere, or reach the host and the tailnet through the bridge gateway. A `DOCKER-USER` rule (or an egress proxy) must be enforced, survive a reboot and be in LOCKDOWN. Because the Funnel sidecar shares the container's namespace and needs the Tailscale control plane, relays and peers, a bare "drop all but two IPs" rule would break Funnel or be widened until it limits nothing. So the rule has two parts: the sidecar's traffic is allowed by named destinations (or an egress proxy with a hostname allow-list), and the MCP process is limited to the sync server and the tenant by that proxy's hostname allow-list. The Auth0 tenant is CDN-fronted, so it is allowed by hostname, never by IP rules. The tailnet reach is limited by the node's tailnet policy above. This is the one mitigation that turns "documented" into "enforced".
- **Per-source rate limit proven through Funnel (task 6.2, now its own story sc-2278): required.** The limit relies on Funnel's `X-Forwarded-For`; until staging shows real client addresses and no `source-unresolved` record, production would run with a shared `loopback` key, which brings back the lockout.
- **Coarse aggregate ceiling (sc-2265): required.** The per-source limit has no cap across sources, so many sources can guess the client secret in bulk. The secret's size and PKCE make that impractical, but production data justifies the cheap bound; the number is reviewed by the Architect and Security Analyst so it cannot recreate the lockout. The ceiling SHALL NOT let a flood from many sources refuse the signed-in user's sign-in; if no global number can meet that, the /48 (IPv6) or /24 (IPv4) tier is used instead.
- **Funnel on one dedicated node: required** (Decision 13).
- **Secret files owned by the container's numeric uid, 0400 for the session token and 0600 or tighter for the rest, proven by the container starting: required** (the Architect's ruling on PR #198; a root-owned file does not work with a non-root container).
- **The data copy only in the container's data directory**, readable only by its uid, removed with the container.
- **A revocation drill rehearsed once on staging,** and **the image built from the reviewed commit with its source commit, tag and digest recorded** in the deployment checklist. The checklist also states whether VPS snapshots or backups include the container's data directory.
- **The token is not an administrator's** (checked by the entry at start, see the spec).
- **The OpenID backstop and roles on production** (`production-identities`), **and the account split (sc-2069)**, so a fresh agent session lists no production tool.
Not required, and tracked elsewhere: an edge allowlist of Anthropic's addresses (optional hardening), the sc-2091 subject on refusal records, and digest pinning (in sc-2203).

### 15. The lockdown dependency: Ken's open decision
Agents hold root on the VPS until LOCKDOWN (sc-563) is done. With root they can read the production container's secret files and its plaintext data directory, bypassing every control above. This change does not decide whether going live waits for the lockdown. It states both outcomes and the spec requires one of them to be recorded: **(B) is more than a risk acceptance:** `production-identities` makes the lockdown a precondition of the OpenID switch ("LOCKDOWN comes first", sc-2060 blocked by sc-563), and this connector needs the session token that switch mints, so choosing (B) also means changing that change. **(A) lockdown is a precondition:** the deployment is blocked on sc-563 and the residual risk in threat 18 is removed; **(B) it is waived:** `production-identities` is changed too, and the residual risk (the session token, signing key, client secret and plaintext copy are readable by agents with root) is accepted by Ken in the threat model. The recommendation is (A), because the plaintext copy and the session token are the very assets the lockdown protects, and the connector is useful only to the assistant while the data at rest is reachable by every agent; but the decision is Ken's.

## Unverified, settled by staging verification (not assumed here)
- Which source addresses Anthropic's connector calls use, and so whether an edge allowlist is worth adding (it is not available behind plain Funnel).
- The callback URL used by each client: claude.ai, the mobile apps and Claude Duet. Duet's connector mechanism is undocumented as far as the Explore found, so the design stays on standard OAuth 2.1 (protected-resource and authorization-server metadata, PKCE, resource indicators) with a configurable redirect allowlist.
- Whether the current connector beta accepts our authorization server with a pre-registered client.

The requirement "Clients are supported only after they connect on staging" turns these into checklist items.

## Risks / Trade-offs

- **A public endpoint for budget data.** Mitigated by one identity, short tokens, read-only in code, and for production a separate tenant, a BASIC-role assistant user, a session token instead of the shared password, and the go-live prerequisites of Decision 14.
- **Plaintext budget copy and the session token on the server.** Accepted for staging. For production the copy lives only in the container's own data directory, readable only by its uid and removed with it; the encryption key on the server weakens end-to-end encryption, so if the production budget is encrypted that key needs a decision of its own (Ken's, in the deployment checklist).
- **Every agent session gets a path to the budget.** Connectors on Ken's account also appear in Claude Code sessions. Pointing the connector at staging is within what agents already reach; pointing it at production is not, so production needs the account split (sc-2069), a LOCKDOWN entry, and Ken's decision on the lockdown (Decision 15).
- **Maintaining OAuth code.** Kept small by using the SDK's router and one provider for one user; a dependency on an external service is avoided on purpose.
