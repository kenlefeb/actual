# Design

## Context

See proposal.md, specs/paychecks/spec.md and ADR 2 (`docs/adr/0002-paycheck-definition-is-source-of-truth.md`).

- **How the API reaches schedules:** `packages/api` methods call `send('api/…')`. In `loot-core/src/server/api.ts`:
  - `api/schedule-update` (line 1054) loads the schedule, applies `fields` (name, posts_transaction, payee, account, amount, date) and calls the internal `schedule/update`.
  - `api/schedule-delete` (line 1196) calls `schedule/delete`.
  - `api/rule-update` (line 989) calls `rule-update`, which can rewrite a schedule's rule, and so its conditions.
  - `api/rule-delete` already fails for a rule that has a schedule (`transactions/transaction-rules.ts` `deleteRule`).
  - Every one of these is wrapped in `withMutation`.
- **How the app reaches them:**
  - Paycheck save, delete and skip run `paycheck-create`, `paycheck-update`, `paycheck-delete` and `paycheck-skip-next` (`server/paychecks/app.ts`). These call the internal schedule functions directly (`writePaycheckSchedules`, `deleteSchedule`, `setNextDate`).
  - `account-set-business-days` regenerates paychecks the same way.
  - The schedule editor and Schedules page send `schedule/update`, `schedule/delete` and `schedule/skip-next-date`.
  - None of these go through `api/…` handlers, so a guard in the `api/` handlers can't affect the app.
- **How a schedule is known to be paycheck-generated:** a live (`tombstone = 0`) paycheck's `definition` lists it as `paySchedule` or as a `deposits[].schedule` (ADR 2). `setAccountBusinessDays` already finds paychecks by id with `definition LIKE '%"<id>"%'` and then parses the definition.

## Goals / Non-Goals

**Goals:**
- API scripts can't change or remove a paycheck's schedules, and the error tells them where to go.
- The app's behaviour, and API behaviour for every other schedule, is unchanged.

**Non-Goals:**
- Guarding internal handlers (`schedule/update` and others) or `internal.send` from API scripts. These aren't the public API.
- Schedules a paycheck generated but no longer lists, after a concurrent edit (sc-556). They aren't "managed" by this definition and the guard lets them through. The reconcile in sc-556 handles them.

## Decisions

### Guard in the `api/` handlers, not in `schedule/update` or `schedule/delete`
Each guarded handler first looks up the managing paycheck, and throws `APIError('This schedule is managed by paycheck "<name>". Edit the paycheck in the app.')` before any read-modify-write. `withMutation` then has nothing to undo.
- **Why:** the internal handlers are shared by the app's schedule editor, which is allowed to edit generated schedules (ADR 2), and by the paycheck code itself. Guarding there would need a "caller is the paycheck code" bypass flag.
- **Alternative:** a schema-level `managed_by` column on schedules. Rejected because it needs a migration and duplicates what the definition already stores (ADR 2).

### One lookup in the paychecks module
Export `getPaycheckManagingSchedule(scheduleId): Promise<{ id, name } | null>` from `server/paychecks/app.ts`:
- `SELECT * FROM paychecks WHERE tombstone = 0 AND definition LIKE '%"<id>"%'`, the same pattern as `setAccountBusinessDays`;
- then an exact check against `paySchedule` and `deposits[].schedule` after parsing, so an id that only appears elsewhere in the JSON doesn't match.

For `api/rule-update`, find the schedule with `rule = <rule id>` first, then use the same lookup.
- **Alternative:** a reverse index kept in memory. Rejected because API calls are rare and the `LIKE` query runs over a few rows.

### `updateRule` is included
A schedule's conditions live in its rule, so `updateRule` on that rule is the same edit by another door. Guarding only `updateSchedule` would leave the drift the story is about (Product decisions 1).

### Docs
In `reference.md`, add a sentence under `updateSchedule`, `deleteSchedule` and `updateRule`: schedules generated by a paycheck are managed by the app, and these calls fail for them with the error above. Also fix the existing copy-paste text under `updateSchedule`, which says "rule" where it means schedule. That's a one-word fix in the same paragraph.

## Product decisions

For the Product Owner to confirm (recommendations given):

1. **`updateRule` on a paycheck schedule's rule:** recommendation: refuse it too, as specified, because it changes the schedule's dates and amounts. If the PO wants the narrower scope, drop the "edits the rule" scenario and the `api/rule-update` guard.
2. **Error wording:** the story's sentence, used for all three calls.
3. **API scope:** only `updateSchedule`, `deleteSchedule` and `updateRule`. `createSchedule` can't target an existing schedule, and the API has no skip or post calls.

## Risks / Trade-offs

- [Scripts that edited paycheck schedules on purpose now fail] → That's the intent. The error names the paycheck, and the docs explain why.
- [A paycheck renamed on another device not synced yet] → The error shows the name this device has. That's harmless.
- [Implementation touches `server/paychecks/app.ts`, which other developers are working in] → The lookup is a new exported function at the end of the file. Coordinate through the Director when this is applied.

## Migration Plan

None. Rolling back removes the guard.
